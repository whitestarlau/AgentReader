# WebDAV 先行：实现方案与「一条龙」接入设计 v0.1

> 生成时间：2026-11-25 | 状态：设计 + 可运行原型（未接主进程）
>
> 实施任务分解见 [`sync-implementation-plan.md`](sync-implementation-plan.md)（P0–P5、S-01~S-24、写盘审计、验收标准）。
>
> 决策：**这一版只做 WebDAV**，但保留 [`sync-research.md`](sync-research.md) §3.1 的后端抽象层——以后加 Gist / Google Drive / OneDrive 只是往注册表里再塞一个 `SyncBackend`，不碰引擎。
>
> 用户诉求原话：「对于受支持的网站提供一条龙的服务，只需要用户登陆坚果云、InfiniCLOUD 的账号就好」。
>
> 本文回答三点：① 这句话在 WebDAV 上能做到什么程度；② 那么「更人性化」应该长什么样；③ 怎么实现。

## 0. 结论先行

**「只登录账号」做不到 —— 但可以把「做不到的那一步」压缩到 30 秒以内，并且用户全程不用离开应用、不用记任何 URL。**

原因是协议层的，不是产品层的：WebDAV 是 HTTP Basic 认证，凭据就是「用户名 + 一个密码字符串」。而坚果云和 InfiniCLOUD 都**强制要求这个密码不是登录密码，而是单独生成的应用密码**。两家都没有对个人开发者开放 OAuth（InfiniCLOUD 官方文档原文：「At this time, OAUTH2 access is not open to the public」）。所以「用户输入账号密码 → 应用静默换取 WebDAV 凭据」这条路在法律与技术上都不通。

但如果按「账号密码能不能直连」把服务分成两档，结论就没那么悲观：

| 档位 | 服务 | 用户实际要做的 | 一条龙成色 |
|---|---|---|---|
| **真·一条龙** | Nextcloud / ownCloud、群晖 WebDAV、自建 | 填 URL + 账号密码，点连接 | **full**：一次表单到底 |
| **引导式** | 坚果云、Koofr | 应用内打开登录窗 → 在「第三方应用管理」点生成 → 回到应用点「从剪贴板读取」 | **guided**：多两步，但零信息检索。Koofr 额外有个坑：密码错太多次会锁号 1 小时（见 §1） |
| **引导式 + 自动探测** | InfiniCLOUD | 同上，且**不用手填 URL**——它的 WebDAV 地址是每账号一个 `<node>.infini-cloud.net`，我们用官方 REST API 自动反查 | **guided**：最省事的一种 |

也就是说：**「只需要登录账号」在自建类服务上是真的；在坚果云/InfiniCLOUD 上是「登录 + 点一下生成 + 粘贴一次」，而所有 URL、路径、协议细节都被预设表吃掉。**

这套设计已经在 [`research/webdav-presets.ts`](research/webdav-presets.ts) 里跑通了（预设表、端点归一化、InfiniCLOUD 反查、错误映射、状态机、请求预算，6 组断言全绿）。

## 1. 关键事实核对（2026-11-25 实查，非推测）

| 事实 | 来源 | 对设计的影响 |
|---|---|---|
| 坚果云 WebDAV 端点是 `https://dav.jianguoyun.com/dav/`，凭据为「账号 + **应用密码**」（账户信息 → 安全选项 → 第三方应用管理 → 添加应用密码） | 坚果云帮助中心《坚果云第三方应用授权WebDAV开启方法》 | 预设里端点写死，用户只需填账号 + 应用密码；应用内要能直达那个页面 |
| 坚果云 WebDAV：单文件 500MB，免费版 **600 请求 / 30 分钟**，单次列目录最多 750 项（需翻页） | 同上 | `caps.maxObjectSize`、`caps.requestBudgetPerMinute = 20`；列表必须分页 |
| 坚果云没有对个人开发者开放的 API / OAuth（官网探测 `/s/openplatform`、`/s/developer` 均无对应页面） | 官网探测 | 不能自动生成应用密码，只能引导 |
| InfiniCLOUD 的 WebDAV 地址**按账号不同**：`https://{node}.infini-cloud.net/dav/`（或旧域 `.teracloud.jp`） | InfiniCLOUD Developers › Authentication methods | 端点不能写死 → 必须走反查或让用户手填 |
| InfiniCLOUD 提供 BASIC 认证的 REST 接口 `GET https://api.infini-cloud.net/v2/api/ba/user`，带 `Basic(账号:应用密码)` + `X-InfiniCLOUD-API-KEY`，返回 JSON 里含 `node` 与 `webdav_url` | InfiniCLOUD Developers › REST API V2 | **用户不用填 URL**，这是它的官方「只需 ID 和密码」路径 |
| 该 REST 接口需要**应用侧申请 API KEY**（个人 / 开源均可申请，需官方确认身份），API KEY 不是秘密、可以公开 | 同上 | 我们内置一个 key 并允许在设置里覆盖；申请是一次性的 |
| 2021-06-02 16:25 之后注册的 InfiniCLOUD 账号，BASIC 认证（WebDAV）**默认关闭**，必须在 My Page 打开「外部应用连接」并生成应用密码 | 同上 | 403 的错误文案必须点名这一条，否则用户会卡死 |
| InfiniCLOUD 的 OAuth2 通道「尚未公开」 | InfiniCLOUD Developers › REST API V2 | 别等它，也别假装能做 SSO |
| Koofr 的 WebDAV 端点是 `https://app.koofr.net/dav/Koofr`，**大小写敏感**（`/dav/koofr` 会 404）；用户名为注册邮箱，密码必须是「应用特定密码」 | Koofr 帮助 › How do I connect a service to Koofr through WebDAV | 预设里端点写死且不做小写归一；404 文案要点名大小写 |
| Koofr 官方明确：**没有应用特定密码就无法建立 WebDAV 连接**，且建议每次新连接生成一个新密码 | Koofr 帮助 › Which password do I need to use… | 401 文案同样要写「不能用登录密码」；提示「每台设备单独生成一个」 |
| Koofr 的 **429 不是限流，而是密码错误次数过多 → 账号临时锁定 1 小时** | Koofr 帮助 › I am getting a 429 error message… | **绝不能自动重试**（越重试锁得越久）；错误语义必须按服务覆盖，见 §3.3 |
| Koofr 的 412 被官方归为「客户端问题」；423 是别的应用持锁未释放 | Koofr 帮助 › 412 / 423 两篇 | `If-Match` 要用对，否则宁可只做写后回读；423 可退避重试 |
| Koofr 免费 10GB（另有 10GB 邀请赠送），WebDAV 端点实测可达（未带凭据返回 401，说明路径存在） | koofr.eu/pricing、对 `/dav/Koofr/` 的探测 | 预设表免费额度按 10GB 写 |
| 坚果云/InfiniCLOUD 的账号密码都不接受用于 WebDAV | 两家文档 | 401 文案必须明确写「不能用登录密码」，这是最高频的失败 |

> 这几条里最有价值的是第 5 条：它是「一条龙」唯一真正的自动化入口。没有它，InfiniCLOUD 用户要自己去 My Page 找「你自己的那个 URL」，这是所有 WebDAV 客户端都把用户劝退的地方。

## 3. 连接向导：「更人性化的页面」具体长什么样

### 3.1 五步，一屏一屏推进

```
pick-provider → credentials → verify → scope → first-sync → done
                    ↑            │
                    └── failed ──┘        （失败只能回退到凭据步，不能跳步）
```

状态机已在原型里实现（`reduceWizard`），规则有两条值得写死：

- **不允许跳步**：没选服务不能填凭据，没验证通过不能选范围。跳步是「状态错乱」类 bug 的主要来源。
- **失败带上下文回退**：`{ step: "credentials", failure }`，表单保留已填内容，错误提示挂在具体字段上，而不是弹一个 `alert` 再把用户清空。

### 3.2 三个关键屏

**屏 1：选服务**（卡片，不是下拉框 —— 下拉框藏掉了「免费额度」这个决策信息）

三处刻意的设计：

- **「余额：本窗口已用 3 次请求」**：坚果云 600/30min 是真实约束，把它变成可见的仪表，比藏在文档里强。用户看到「3/600」就不会再问「为什么同步要等」。
- **「发现云端已有 12 本书」**：把 VSCode 反过来的教训（新设备拿空状态覆盖云端）在 UI 上提前说清，让用户知道这是「合并」而不是「覆盖」。
- **原书开关的副标题不是「可选」，而是「会占用你网盘的流量配额」**：说清代价，而不是让用户事后发现 1GB 用完了。

### 3.3 错误文案：每种失败都给「下一个动作」

`classifyFailure()` 覆盖 401 / 403 / 404 / 405 / 423 / 429 / 507 / 网络 / TLS，每条都是「标题 + 一句人话 + 一个按钮」。其中三条是专门为这两家写的：

| 状态 | 用户看到 | 按钮 |
|---|---|---|
| 401 | 账号或应用密码不对。坚果云 / InfiniCLOUD 的 WebDAV **不接受登录密码**，必须用「应用密码」。 | 打开生成页面 |
| 403 | 凭据正确但目录不可写。InfiniCLOUD 需要在 My Page 打开「外部应用连接」。 | 打开 My Page |
| 429（坚果云） | 请求太频繁（免费版 600 次/30 分钟），已自动退避，无需操作。 | —（自动重试） |
| 429（Koofr） | 账号被临时锁定 1 小时：Koofr 的 429 不是限流，而是密码错太多次。确认填的是应用特定密码；**这期间重试只会延长锁定**。 | 打开生成页面 |
| 412 | 远端文件在你读取后被别的设备改过（条件写被拒），已自动重新拉取并重试。 | —（自动重试） |

这三条覆盖了实测中 90% 的首次连接失败。把「你必须用应用密码」写进 401，是投入产出比最高的一句文案。

### 3.4 内嵌登录窗的安全边界

用户点「生成…」时，我们开一个 `BrowserWindow` 指向服务方页面。这不是「替用户登录」，而是「替用户打开正确的页面」，边界必须写死：

| 规则 | 做法 |
|---|---|
| 不落 cookie | `webPreferences.partition = "sync-login"`，且**关闭窗口即 `session.fromPartition("sync-login").clearStorageData()`**，下次用要再登 |
| 不读页面内容 | 不向页面 `executeJavaScript`，不监听 `did-get-response-details`，登录态不回流主进程 |
| 不拿用户密码 | 应用只接收「应用密码」这一个字段，且只经剪贴板或手输进来 |
| 导航白名单 | 只允许 `jianguoyun.com` / `infinicloud.com` / `teracloud.jp` / `sso.infinicloud.com` 及其子域；其他链接一律 `shell.openExternal` |
| 深链会失效 | 预设表里既存「深链」也存「帮助页 URL」，深链打不开时自动回落到帮助页（`openExternal`），保证永远有一条出路 |

坚果云的后台是内部路由（`/d/account/...`），随时可能改版，所以**不要硬编码成唯一入口**，一定带帮助页兜底。

### 3.5 剪贴板

只在用户**点按钮时**读一次 `clipboard.readText()`，不做后台监听。理由有两层：macOS 14+ 会弹系统级「允许粘贴」提示，后台读会让用户困惑；后台监听剪贴板在安全直觉上也很糟。读到之后在输入框下方显示「已读取 24 个字符的密码 ✓」，不显示明文。

## 4. 实现结构

### 4.1 目录

```
packages/app/src/main/sync/
  backend.ts          ← 抽象层（保留，WebDAV 只是它的一种实现）
  backends/
    webdav.ts         ← 本次唯一实现：PROPFIND / PUT / GET / MKCOL / MOVE / DELETE
    local-folder.ts   ← 零成本，用它做「两台机器」的本地联调（强烈建议同时做）
  presets.ts          ← §3.2 那张表，纯数据
  connect.ts          ← 向导逻辑：归一化、反查、验证、错误映射（本原型直接搬）
  engine.ts           ← pull → merge → push + 队列 + 限流 + 写后回读（后端无关）
  config.ts           ← 后端配置与凭据（safeStorage），不进同步体
  base.ts             ← 基线快照
```

`engine.ts` 里不出现任何 `if (backend === "webdav")` —— 这是「保留抽象层」的验收标准。

### 4.2 WebDAV 后端要点（按踩坑顺序）

| 事项 | 做法 |
|---|---|
| 认证 | **preemptive** Basic：第一次请求就带 `Authorization`，别等 401 挑战（多一次往返，坚果云配额敏感） |
| 列目录 | `PROPFIND` + `Depth: 1` + 只要 `getcontentlength` / `getlastmodified` / `getetag` / `resourcetype`；响应可能 750 项截断，用 `resourcetype` 判断子集合后继续 `Depth: 1` 递归 |
| XML 解析 | 40 行正则/手写解析即可（只要四个字段）；坏 XML 一律按「列表失败」处理，不要半解析 |
| 建目录 | `MKCOL`；父目录不存在要逐级建（`409` 是「父不存在」的信号），建之前先 `HEAD`/`PROPFIND` 判存在 |
| 写 | `PUT`；`If-Match: <etag>` 支持时用，不支持时（返回 412 就说明支持）靠「写后回读」兜底 |
| 大文件 | 分片 `PUT` 到 `tmp/{docId}.part.{n}`，全部成功后 `MOVE` 拼装；`MOVE` 不支持时退货为「一次整传 + 大小预检」 |
| 限流 | 令牌桶 20/min（坚果云）、60/min（InfiniCLOUD / Koofr）；`429` 读 `Retry-After`，无此头则指数退避 1→2→4…上限 5min |
| **429 语义按服务区分** | 坚果云 429 = 限流（退避重试）；Koofr 429 = 密码错太多次的账号锁定（**立即停止，禁止重试**）。所以 `classifyFailure` 返回的 `retryable` 必须驱动引擎的调度，而不是只驱动 UI 文案 |
| 412 | 条件写被服务方拒绝（远端已变）。不要直接报错：重新 `GET` → 重新三方合并 → 重试，上限 3 次；Koofr 尤其如此，它把 412 归为「客户端问题」 |
| 大小写 | Koofr 端点 `/dav/Koofr` 的 `K` 必须大写。归一化函数只补尾斜杠、**不改变大小写** |
| 超时 | `AbortSignal.timeout(15_000)`；大文件上传走 60s |
| 空目录 404 | 有些服务对不存在的目录返回 `404` 而非 `207 []`，视为空列表，不要当错误 |
| 中文文件名 | 一律自己 `encodeURIComponent` 每一段，别整体编码路径（会把 `/` 编掉） |

### 4.3 IPC 面

```
sync:presets            → SyncPreset[]（渲染进程直接渲染卡片）
sync:probe              → 用账号+应用密码反查端点并验证（InfiniCLOUD 专用）
sync:test               → PROPFIND 根目录，返回 { ok, freeBytes?, requestCount }
sync:configure          → 保存后端配置（凭据走 safeStorage）

sync:now / sync:resolve / sync:conflicts
```

## 5. 同步引擎（WebDAV 版）

请求数（实测口径见原型 C6）：50 本书、本次 3 本有变化、带设置 → **12 次请求**；50 本全变 → **153 次**，都远低于坚果云 600/30min。Koofr 与 InfiniCLOUD 没有公开的请求配额（Koofr 的 429 是账号锁定而非限流），但令牌桶仍按 60/min 保守限速，避免把第三方服务打出异常。

```
pull():
  GET manifest.json                     1
  对每个 rev 落后的 doc: GET state/{docId}.json   N
  merge3(base, local, remote) → 写本地
push():
  pull() 先行（基线有效性的前提）
  PUT state/{docId}.json + 回读 GET     2N
  PUT manifest.json                     1
```

三条不变式：

1. **push 前必须 pull**（否则退化成覆盖式同步）；
2. **manifest 最后写**（中途失败最多导致清单落后，靠列目录兜底）；
3. **写后回读**（WebDAV 的 ETag 支持不一致，`If-Match` 不能当唯一防线）。

## 7. 待实测（WebDAV 专属，上线前必须逐项验证）

1. 坚果云 `PROPFIND` 是否支持 `Depth: 1` 返回全部四个属性；`quota-available-bytes` / `quota-used-bytes` 是否提供（决定「可用空间」能否显示）。
2. 坚果云对**账号密码**用于 WebDAV 的确切响应（预测 401）——把这条写进 401 文案前要实测，避免误导。
3. 坚果云 `PUT` 是否返回 `ETag`、`If-Match` 是否生效（不生效会返回什么）。
4. 坚果云 600 次/30min 的计数口径：是否含 `PROPFIND`、按账号还是按 IP、超限返回 429 还是 503 且是否带 `Retry-After`。
5. 坚果云列目录 750 项截断的实际表现：`PROPFIND` 是返回部分结果还是报错，需不需要 `Depth: infinity`（多数服务已禁用）。
6. InfiniCLOUD `ba/user` 的 API KEY 申请周期，以及 `X-InfiniCLOUD-API-KEY` 与旧头 `X-TeraCLOUD-API-KEY` 的兼容情况（文档两处写法不一致）。
7. InfiniCLOUD My Page 中「外部应用连接」的**确切开关位置与名称**（决定 403 文案怎么指路）。
8. 坚果云后台「第三方应用管理」的深链 URL 是否稳定；打不开时帮助页兜底是否可用。
9. `MOVE` 在坚果云上是否可用于分片拼装；失败时的回退路径（整传）是否可接受。
10. 中文路径 / 中文文件名在各家的编码行为（`encodeURIComponent` 逐段编码是否都接受）。
11. Koofr：`PROPFIND` 是否返回 `ETag`；`If-Match` 失效时是 412 还是被静默忽略（决定要不要启用条件写）。
12. Koofr：错误密码第几次开始返回 429、锁定时长的确切规则（官方写 1 小时），以及锁定期间 `PROPFIND` 是否也一并被拒。
13. Koofr：应用特定密码的生成页深链（`app.koofr.net` 内部路由）是否稳定；打不开时回落到帮助文章是否可用。
14. Koofr：单文件大小上限（官方只提到 Windows 客户端 50MB 的**客户端**限制，服务端上限未知）。

## 8. 风险

| 风险 | 对策 |
|---|---|
| 用户坚持「为什么不能直接用登录密码」 | 401 文案直接解释原因 + 一键跳生成页；帮助文档补一句「这是网盘的安全策略，不是本应用的限制」 |
| 深链失效（服务方改版） | 预设表同时存深链与帮助页，深链失败自动回落；预设表随版本更新 |
| 内嵌登录窗被服务方判定为异常流量 | 用独立分区、正常 UA、不注入脚本、不做自动化；本质上它就是个小浏览器 |
| 坚果云 600 次配额被打爆 | 令牌桶 + 每本书一个文件 + 请求余额可见；原书默认关 |
| InfiniCLOUD API KEY 申请不下来 | 反查是「增强」不是「必需」：没有 key 时回退成「手填 URL」，预设表里 `endpointProbe` 缺失就是这条路径 |
| 自建服务用自签证书 | TLS 错误单独分类，给「在系统里信任证书」的指引，**不提供「跳过校验」开关** |
